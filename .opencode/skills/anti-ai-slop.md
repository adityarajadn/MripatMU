Anti-AI-Slop Orchestrator
Coordinate the smallest set of focused skills needed to ground, simplify, and verify a digital artifact.

Operating principle
Use the smallest coherent visual, verbal, and behavioral system that preserves:

the user's primary task;
the artifact's verified content;
necessary functionality;
accessibility;
the author's or product's specific identity;
maintainable component and interaction contracts when reusable UI or action governance is in scope.
Do not infer that an artifact was generated by AI from style alone. Report observable slop signals, not authorship.

Required inputs
Use what the user supplied:

artifact or source files;
screenshot, URL, markup, component tree, or design tokens;
design library, documentation, code, tests, or live usage when component behavior, interaction governance, or parity is in scope;
intended user, primary task, and material decision contexts;
visible, contextual, disclosed, or unavailable action paths when relevant;
real copy, claims, dates, prices, outcomes, and constraints;
approved product voice, terminology, nearby copy, and every locale in scope;
target platform and release stage;
current inventory, ownership, legacy mappings, and adoption plan when a design system is being introduced or migrated.
When critical evidence is absent, record it as unknown. Do not invent it.

Quick pass
Use for a small artifact, an early draft, or an explicit request for a fast review without release verification.

Run slop-signal-audit once in its quick-pass mode: no category scores, no quality or slop-risk score, and no verdict.
Report up to five material changes with evidence labels and locations. Never pad the list; fewer findings are a valid result.
Apply the changes only if the user asked for edits; otherwise stop at the report.
State plainly that accessibility, reflow, component and interaction parity, design-system adoption, and reduced-motion behavior were not verified, and offer the full workflow as the follow-up.
A quick pass must still respect the decision gates below. It may skip verification and scoring; it may not skip evidence labeling or invent support. Directly observed hard failures are still reported, without a release decision.

If the client supports skill invocation, activate the listed focused skills. Otherwise execute the same sequence using the contracts in references/composition-map.md.

Evidence labels
Label every material statement:

Observed — directly present in supplied material.
Measured — produced by a deterministic check.
Inferred — reasoned from evidence; state that it is an inference.
Unknown — not verifiable from the supplied material.
Never convert inferred or unknown material into a factual claim.

Decision gates
Do not issue a passing result while any of these project hard failures remain:

fabricated customer, metric, quote, award, result, capability, or case study;
mock or generated UI presented as proof of a real product capability;
removal of keyboard focus, form labels, errors, text alternatives, or semantic structure for visual cleanliness;
scroll hijacking without an equivalent user-controlled mode;
essential information available only through motion, color, hover, or pointer-only interaction;
nonessential interaction motion without a reduction or disable path;
content that cannot reflow without loss at the target accessibility baseline;
required component behavior documented in design or guidance but absent from the implementation or required live usage;
a required component state or accessibility behavior that remains failed or unknown;
a misleading affordance that makes inert content appear operable or maps materially different behavior to the same false expectation;
a required decision context with competing primary actions and no supported equal-priority or no-primary reason;
a required primary, frequent, or recovery action disclosed or unavailable without a supported reason and adequate path;
a required design-system lifecycle that remains failed or unknown when migration or adoption is part of the release scope;
unsupported claims presented with certainty.
A hard failure is a project release gate. It is not automatically a legal conclusion or a complete WCAG conformance determination.

Deliverable
Use assets/full-report-template.md.

Include:

scope and supplied evidence;
primary user, task, and decision contexts;
observed signals;
selected structure;
content gaps and prohibited inventions;
component contract, state coverage, ownership, and design-code parity when in scope;
affordance mapping, action hierarchy, visibility, grouping cues, and design-system lifecycle when in scope;
visual budget, nested-radius relationships, and justified exceptions;
copy decisions with locale, correct/suggest/keep, evidence status, evidence and voice basis, unresolved information, and multilingual or runtime parity when in scope;
motion decisions;
accessibility findings;
deletion plan ordered by impact and reversibility;
verification status;
unresolved unknowns.
Completion rule
Do not optimize for emptiness or uniformity. Stop pruning when the next removal would reduce task completion, comprehension, evidence, identity, component or interaction behavior, action discoverability, migration safety, or accessibility
